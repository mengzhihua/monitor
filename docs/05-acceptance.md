## 2026-09-23 查询和图表优化

TSDB 原始数据与降采样数据在求平均值、最值、总和和末值时，改为直接累加到目标时间格；中位数仍保留排序所需的样本列表。测试覆盖六种聚合方式、加权平均、零计数和空时间格。

同一台 Intel i7-9750H macOS 机器上，`BenchmarkQuery24Hours600Points` 每轮读取24小时历史并聚合为600点，固定30轮：改动前 `530641 ns/op、556379 B/op、1474 allocs/op`，改动后 `500466 ns/op、413614 B/op、34 allocs/op`。内存分配次数下降约97.7%，字节数下降约25.7%；两次短跑的耗时差异不作为稳定吞吐保证。

Web Dashboard 只为视口附近的图表加载历史和订阅实时数据；图表滚出视口后停止周期请求，返回视口时补读历史。周期请求按图表ID分散在30秒内；图表定义未改变时复用现有画布。桌面和手机浏览器测试验证了按需加载、滚动返回后画布复用以及原有登录、长历史、离线恢复流程。

## 2026-09-23 连接状态与凭据写入顺序

Flutter 连接管理增加会话代次检查：退出、切换连接或销毁后，未完成的登录、自动恢复和节点响应不能覆盖新状态。验证成功后一次性发布完整连接，替换连接失败保留原连接；设置和安全存储失败不会关闭已经验证的客户端。节点刷新合并进行中的请求，节点消失后回退到本机并保存选择，应用销毁时关闭其拥有的客户端。

设置与凭据写入共用顺序队列，退出界面立即生效，后台清理必须等正在进行的保存结束，后续登录再保存新凭据。存储警告独立于网络错误，节点刷新成功不会将其清除；即使同时发起的新登录失败，退出清理失败的提示仍然可见。

## 2026-09-23 默认采集器 CPU 开销

macOS Apps 每个 PID 原先分别调用三次 `proc_pidinfo(PROC_PIDTASKINFO)` 取得 CPU、RSS 和线程数，每次还重复装载动态库、查找符号与读取时基。现在三项共用一次系统调用，符号和时基按进程生命周期初始化一次。失败、短读或权限不足不更新 CPU 累计基线，初始化失败回退原有实现；PID 出生标识、IO 读取和采样频率保持原规则。另修复失败读取重用上一轮速率、重复计入用户/用户组 CPU 的问题。回归覆盖结构布局、非1:1时基、实际进程计数一致性、取消、初始化回退，以及失败期间 owner 累计不增长、恢复只计新增 CPU 时间。

`macos` 采集器默认 `sysctl` 仅读取压力、swap 和温度所需3键，使用 `-i` 忽略本机不存在的键；自定义可执行路径继续使用原有 `-a` 参数。`memory_pressure` 和 `pmset` 的指标含义与每次采样频率保持不变。全部来源无指标时明确失败，空温度输出不再导致崩溃，恢复后继续采样。

Darwin/FreeBSD 网络统计的 TCP、UDP 共用一次 `inet` 扫描，Unix 套接字独立读取，外部 `lsof` 调用由每轮3次减为2次；其它平台保持各自读取方式。失败或不支持的次要来源不写入健康零值，取消的读取即使底层错误被吞掉也会报告不可用。连接表仍按原规则筛选、排序、统计总数和截取，仅为返回行读取进程名称与命令行，并缓存本次请求的失败 PID 查询。回归验证混合协议计数、Unix 不误算 TCP、空集、失败与恢复、取消、排序/总数/上限及失败 PID 去重。

## 2026-09-23 macOS 进程身份读取

Apps 采集在 macOS 上复用进程列表中已经取得的名称和启动时间，未缓存的 PID 不再另查一次 `kern.proc.pid`。可能被截断的长名称从命令行首参数展开，并与完整命令行共用一次参数读取。短名称仍允许命令行无权限；长名称无法读取参数时仍跳过，避免按截断前缀误分组。取消操作、PID 复用时丢弃旧身份和 CPU/IO 基线的规则保持，其他平台沿用原来的名称及命令行读取路径。

Intel macOS、相同 Go 工具链，以自建、临时签名的两个休眠进程测量身份读取；每项500ms、重复3次，表中为中位数。基准同时保留旧读取路径，不包含进程枚举、其余指标采样和 HTTP 请求：

| 身份读取 | 原路径 | 快照路径 |
| --- | ---: | ---: |
| 短名称 | 198.65 µs、11次分配 | 50.14 µs、8次分配 |
| 长名称（含空格） | 238.32 µs、17次分配 | 48.72 µs、8次分配 |

这两项局部耗时分别下降约74.8%和79.6%。该路径主要用于首次出现或未能缓存身份的进程；已经缓存身份的 PID 不重复执行，因此不能把这两个比例当作每轮采集或整个服务的降幅。分配字节受系统返回的参数缓冲区大小影响，不据此宣称固定比例内存收益。

## 2026-09-23 macOS 冷启动归属查询

## 2026-09-23 Apps 采样取消与进程查询

Apps 现在先暂存一轮采样，提交前检查取消状态；超时或取消不推进 CPU/IO 基线、累计值、图表和公开进程表。已解析的身份仍缓存，避免冷启动重试从头查询。进入提交阶段后完成本轮更新；这不是所有图表和所有 HTTP 请求之间的数据库事务。暂存切片复用容量，每轮结束清除引用。

进程查询独立复制最近一次完整表，再排序及过滤；读取进程的慢系统调用不再占用查询锁。首次完整采集前返回空表，之后失败时继续返回上一轮，并在 `result.collected_at` 提供实际采集的 Unix 秒时间戳（首次成功前省略），不能把外层请求 `time` 当作采集时间。采集器错误仍通过原有状态接口报告。

进程 CPU 百分比按该 PID 两次有效 CPU 样本之间的时间计算。漏采一秒后恢复的5 ms增量应除以两秒，显示0.25%，而不是0.5%。应用组、用户和用户组累计 CPU 都直接计入同一个实际增量，避免取消造成用户汇总遗漏。单个 PID 漏采后，汇总图仍在恢复时计入累计差值；本轮没有推算缺失区间内各秒的真实 CPU 分布。

把相同回归场景放到旧版 `e1e4f55` 上，复现了三项失败：进程查询等待被阻塞的采样器、取消后基线/公开表变化，以及漏采后的进程比例错误。新版测试还覆盖 CPU/IO 恢复只累计一次、采集时间戳不在取消时更新、冷启动仅缓存身份、暂存引用释放、查询结果互不修改。

## 检查点设计及升级

旧实现每次检查点分别同步每条序列和各层未闭合桶，2000条序列在本机需要249.66秒。新实现复制一致的内存状态后释放采样锁，将原始缓冲区、各层已闭合/未闭合桶合并成一个gzip编码、SHA-256校验的`checkpoint.v1`文件；同步文件、原子替换，再同步目录。磁盘I/O期间仍可采样和查询。写满的数据块保留原有归档格式。

恢复先读取原有块，再恢复检查点并排除重复数据；检查点之后已经归档的原始样本会补入聚合层。创建于检查点之后的新序列也包含在补算中。检查点损坏会明确报错，避免无声忽略已确认数据。单个检查点的压缩前/后大小都限制为512MiB，超出或写失败会显示持久化错误，保留之前的检查点。

- 默认30秒是调度间隔，异常退出的保证只到**最后成功检查点**，不能称为30秒硬性丢失上限。
- `db.persistence`包含检查点时间、错误、耗时和文件字节数；这些字节与各层归档块字节分开统计。
- `tier0_retention_size`约束原始归档块，检查点和rollup另占磁盘；应给活跃缓冲区及备份预留空间。
- 旧版数据可直接读取；升级前仍应停服备份。**旧二进制不能读取新检查点内的未封块数据**，降级应恢复升级前的备份，不能直接使用升级后的数据目录。
- 全块归档仍采用逐序列文件，长期大规模写入、归档时延和恢复速度还须在目标存储上测量。单次小检查点结果不能外推到数百万序列。
