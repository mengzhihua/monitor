# 本机告警规则工作台

本轮以告警配置的完整使用流程为目标：从 Web 查看规则、校验修改及影响范围，再持久化保存。之前的动态 API 修改只存在于进程内；升级后，动态规则、禁用和删除标记都保存在数据目录，服务重启后自动恢复。

## 对标结论与范围

以下对照于 2026-09-28 查阅官方资料；描述本轮交付范围，不代表完整兼容或全量功能对齐。

| 行业能力 | 本轮实现 | 仍有差距 |
| --- | --- | --- |
| [Netdata 动态配置](https://learn.netdata.cloud/docs/alerts-%26-notifications#4-dynamic-uiapi-configuration-override)：配置分层，动态修改可持久保存与重置 | 启动配置作为基础，动态覆盖单独保存；支持恢复当前配置规则 | 只管理当前服务的本机规则，未实现 Hub 向远端 Agent 下发 |
| [Grafana 规则编辑](https://grafana.com/docs/grafana/latest/alerting/alerting-rules/create-grafana-managed-rule/)：保存前预览 | 校验语法、容量及版本，显示匹配图表数量与前 50 张图表 | 这是作用范围预览，不执行表达式、不回放历史，也不预测是否触发 |
| [Prometheus 规则校验](https://prometheus.io/docs/prometheus/latest/configuration/recording_rules/)：变更前检查规则 | 整批编译与检查后原子保存；任一规则失败，整批不生效 | 使用本项目表达式，未提供 PromQL 或 promtool 兼容接口 |

优先后续补齐：[Prometheus 的持续触发等待与恢复保持](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)（`for` / `keep_firing_for`）、[Grafana 的无数据与求值错误策略](https://grafana.com/docs/grafana/latest/alerting/fundamentals/alert-rule-evaluation/nodata-and-error-states/)、规则变更审计与历史回退，以及带权限、确认与失败反馈的远端规则分发。当前 `delay` 延迟的是通知，不能当作持续触发等待；当前规则快照不是历史版本库。

## 使用方式

1. 登录 Web，点击顶部 **本机告警规则**。面板显示实际管理的本机主机名；切换指标页的远端节点不会改变规则管理目标。
2. 搜索并选择规则，或新建规则。支持现有全部 `RuleSpec` JSON 字段；已有规则名称固定，新建时可以命名。列表标明配置规则、动态覆盖、自定义和已删除。
3. 编辑 JSON 或切换启用状态，点击校验与预览。修改草稿后原预览失效，需重新校验。匹配数量表示 `on` 与 `chart_labels` 的作用范围，禁用规则也会显示范围。
4. 确认预览后保存。删除基础规则会留下删除标记；删除自定义规则会移除该定义。恢复配置规则移除覆盖或删除标记，露出本次启动时读取的基础定义。
5. 遇到并发修改或服务重启，旧版本保存返回冲突，草稿保留。点击“读取最新并重新核对”后比较当前规则与草稿，再次预览后保存。不会自动覆盖他人修改。

`admin` 可编辑；`viewer` 与 `troubleshooter` 只读。健康引擎关闭时面板明确显示不可用。没有自动轮询或后台预览求值。关闭面板、切换规则和刷新页面时，未保存草稿有离开保护，但不会把草稿写入浏览器长期存储。

如果配置升级后某个已删除规则的基础定义不再存在，仍可清除它的删除标记；此时不会产生一个空规则。

## 持久化与生效边界

- 基础优先级保持 `builtin → health.d → health.alarms`，动态覆盖位于其上。**恢复的是当前启动配置，不保证是发行版内置默认值**。修改原 YAML 后仍需按原部署流程重启。
- 覆盖文件位于 `<data_dir>/health/alert-rules.json`，不改原 YAML。Unix 新文件使用 `0600`；Windows 依赖数据目录 ACL。没有持久化目录的嵌入式 Engine 返回 `persistent=false`。
- 最多 1000 条动态覆盖与删除标记、文件最大 4 MiB；单次 API 请求最大 1 MiB。达到上限会报错，不静默淘汰旧规则。可以删除自定义规则或恢复配置规则来释放容量。
- 文件先写入同目录临时文件并同步，再替换目标；保存失败不会发布内存变更。损坏或无法读取的覆盖文件会阻止健康引擎启动，避免悄悄使用另一套阈值。
- 规则集合版本为不透明字符串，每次保存和服务启动都会改变。所有管理操作要求提交读取时的版本，旧版本返回 `409`。
- 成功修改后，受影响告警实例及尚未派发的分组提醒被清理，下一个调度周期按新定义重新绑定。未变规则保持实例 ID。已进入发送队列或已经发送的通知无法撤回；历史告警日志保留。
- 本版本之前通过 API 临时改动的规则没有持久文件，升级前需从旧进程导出需要保留的定义，升级后再提交；不能自动找回已经退出进程中的修改。

升级或备份时保留整个数据目录。若覆盖文件损坏，先停止服务并备份文件，再修复或从备份恢复；直接移走文件意味着放弃所有动态修改并恢复启动配置。回退到不支持该覆盖文件的旧版会忽略动态规则，应先记录当前有效定义及其对应配置。

## API

| 端点 | 行为 |
| --- | --- |
| `GET /api/v1/alert_config`、`/api/v3/alert_config` | 读取本机规则；含 `revision/persistent/hostname/scope/can_manage`、来源与删除状态 |
| `POST /api/v1/manage/alert-rules/preview` | 校验拟议变更并返回作用范围，不写盘、不改变告警、不发送通知 |
| `POST /api/v1/manage/alert-rules` | 版本一致时保存变更，返回完整新快照 |
| `POST/PUT/DELETE /api/v1/alert_config`、`/api/v3/alert_config` | 保留旧客户端接口；新增持久化、整批原子更新与可选 `?revision=` |

新管理请求使用 `{ "revision": "读取到的版本", "action": "create|update", "config": { ... } }`，或 `{ "revision": "读取到的版本", "action": "delete|reset", "name": "规则名称" }`。全部写入端点与管理预览要求已认证管理员；预览不生成保存令牌，保存时会再次执行全部校验。远端 `?node=` 请求返回 `400`。

旧 POST 为仅新建，PUT 为创建或覆盖，支持单条 JSON、`{"config":{...}}`、`{"alarms":[...]}` 和 YAML `alarms: [...]`。拒绝未知字段、多个文档、混合包装、批次重复名称和无效表达式；名称冲突不再导致半批保存。旧客户端不传版本仍可无条件写入，推荐迁移到新接口或带上 `?revision=`。

错误状态：无效请求 `400`，未认证 `401`，权限不足 `403`，规则或健康引擎不存在 `404`，版本或名称冲突 `409`，请求过大 `413`，容量上限 `422`，存储失败 `503`。写请求若网络响应丢失，先读取当前快照确认结果，再决定是否重试。

## 验证

`make all` 构建嵌入 Web 的服务后，执行 `python3 scripts/verify-alert-rules.py`。它只使用临时配置、随机测试凭据、随机本机端口和静默通知；检查真实内存样本绑定、预览无写入、权限、同版本并发写、旧 API 整批原子性、两次实际重启、规则恢复、文件权限及损坏文件拒绝启动。

Go 回归覆盖文件失败回滚、跨重启版本、深拷贝和调度中删除竞争；Web 回归覆盖管理员编辑、只读、冲突草稿、过期请求与桌面/移动端布局。脚本已纳入 `make acceptance` 和 CI。

本轮本机验收：Web 规则管理及原维护/通知回归共 **36/36** 通过（桌面与移动端）；真实规则验收完成 **两次重启**，并通过默认登录保护、通知及维护计划回归。Go 全包 `vet` 与 `test -race -p 1` 检查覆盖本轮后端修改。跨平台和完整浏览器集由 main CI 继续执行，不能把本机结果当作各部署环境的实机验证。
