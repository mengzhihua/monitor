# 配置安全与系统开销优化

2026-09-27，本轮加强配置并发保护、节点配置读取隔离和凭据文件保存，补齐配置编辑草稿保护，降低运维磁盘指标查询开销，并修复日志取消和短请求连接清理。本文记录实现与已完成的定向验证，不将代码提交、安装包发布或生产部署视为同一结果。

## 配置保存与版本检查

Hub 的期望配置更新现在将版本比较、读取当前配置、计算修改和持久化放在同一锁内完成。多个管理员基于同一版本提交时，只允许一个成功，其余返回 HTTP `409`。禁用采集器的旧式更新保留锁内读取到的最新 YAML；节点上报内容和应用回执不被管理员提交覆盖。写盘失败时恢复此前的内存配置，不发布未保存成功的版本。

Hub 配置的 `updated` 是每个节点单调递增的版本号：取当前 Unix 秒与“上一版本加一”中的较大值，避免同一秒多次保存或系统时钟回拨复用版本。它不再是严格的保存时间戳，客户端应原样回传用于比较，不用它推算实际保存时间。节点的 `report_at` 和应用回执的 `at` 仍表示对应事件时间。管理员接口还按保存顺序向本进程的 Agent 连接排队下发，避免先保存的旧配置在新配置之后入队。

本机配置仍以文件修改时间的 Unix 微秒值作为 `updated`。读取内容及版本时使用同一已打开文件，避免路径被替换后旧内容配上新版本。除了请求进入时的检查，最终写入还在 `config.SaveIfUpdated` 的写锁内重新比较版本，覆盖同一进程通过 `config.Save` 执行的远端配置应用等写入，避免检查通过后又覆盖其他写者的更新。

两种接口都区分显式 `if_updated: 0` 与省略字段：

| 请求 | Hub 期望配置 | 本机配置文件 |
| --- | --- | --- |
| 指定非零版本 | 必须与已读版本一致 | 必须与已读文件修改时间一致 |
| 显式 `0` | 要求尚未保存期望配置；已有节点上报不等于已有期望配置 | 要求配置文件仍不存在 |
| 省略 `if_updated` | 保留旧客户端的无条件更新行为 | 保留旧客户端的无条件更新行为 |

本机写锁只协调本进程使用该保存函数的写者，**不是跨进程文件编辑锁**。外部编辑器不参与该锁；文件时间戳也不是内容散列。需要人工修改部署配置时，应协调写入时机，不能把 API 的版本比较理解成对任意外部写入的完整事务保证。

## 凭据文件与节点读取隔离

配置文件和 `.bak` 备份分别使用同目录新建的私有临时文件，写入并同步后以重命名替换。Unix 上新文件权限为 `0600`；备份失败时不继续覆盖当前配置。备份与当前文件是两个独立替换步骤，不是两文件原子事务。内容相同的保存不轮换原备份，也会检查并收紧旧备份的权限，保留其原始内容。

Hub 的 `org.json` 含静态流密钥及节点期望/上报 YAML，也改用私有临时文件保存。加载旧文件时就检查并收紧权限，即使升级后只有读取请求也会执行迁移；迁移失败会报告错误。配置、备份和组织文件的替换不会通过目标符号链接修改其他文件权限；旧固定 `.tmp` 路径也不再用于写入。符号链接目标的原副本不会因此删除或收紧权限，部署中已有的外部副本仍需独立保管。

Windows 的 Unix 权限位不等于访问控制。该实现不为 Windows 配置目录自动建立私有 ACL，部署时仍须通过目录/文件 ACL 限制其他用户读取。

Agent 使用静态密钥按节点 ID 获取配置时，除了密钥当前有效，还必须匹配该节点注册时保存的密钥绑定。未知节点、仅来自副本的节点和旧版未绑定节点须先完成注册。独立 claim 凭据可以在注册前读取所认领节点的配置，但不能指定另一个节点 ID，也不能覆盖已有节点的密钥绑定。重复认领同一节点会被拒绝；旧版本创建的冲突 claim 也不能读取已绑定其他密钥的节点配置。含配置内容的响应设置 `Cache-Control: no-store`。

这个隔离边界是**密钥信任域**：使用不同密钥的节点不能跨域读取配置；共用同一静态密钥的节点仍属于同一信任域，不能据此宣称逐节点隔离。需要独立边界时，应给节点分配不同密钥或使用独立 claim 凭据。

## 配置界面与请求生命周期

- 草稿与开始编辑时的版本绑定；后台刷新只更新服务器副本及节点状态，不悄悄推进草稿的提交版本。
- 遇到 `409` 保留 YAML 或表单草稿，展示最新服务器配置并暂停保存。用户可先复制草稿，再显式载入最新配置重新编辑。
- 节点编辑优先使用 Hub 已保存的期望 YAML；尚未保存时才使用节点最近上报内容，避免上报延迟使编辑器回退到旧配置。
- 切换表单/YAML、切换节点或关闭有修改的面板前要求确认；顶栏“配置”按钮与面板关闭按钮共用检查。页面离开时也提示未保存修改。
- 显式重新加载期间锁定相应编辑器，防止晚到的响应覆盖请求期间新增的输入；节点定时轮询不会抢占该刷新。普通后台轮询不锁定编辑。
- 节点切换、配置页签切换和组件卸载时取消相应未完成的读取，并检查请求身份及节点 ID，忽略过期响应。保存过程中禁止关闭和编辑，避免提交内容与界面状态错位。

macOS 持续日志采集取消时会主动关闭本进程读取的标准输出管道。即使命令的子进程继承了管道，扫描器也能解除等待，随后回收主命令，避免只依赖 `WaitDelay` 却一直阻塞在读取阶段。

Agent 的 claim 兑换和配置拉取使用独立短生命周期 HTTP 客户端，结束后显式关闭该客户端的空闲连接，减少重复控制请求遗留的连接和相关 goroutine。正在使用的流式连接不通过这条清理路径处理。

## 运维磁盘指标基准

原实现为每个节点调用 `Registry.Charts()`，复制并按优先级/ID 排序全部图表，然后才筛选 `disk.space`。现在通过 `ChartsByContext("disk.space")` 在读锁内只收集匹配图表，仅对结果排序。仍会扫描注册表，时间复杂度为 O(N + K log K)，其中 N 是全部图表数、K 是磁盘图表数；没有引入上下文缓存或修改采样周期。新增、替换和删除图表无需维护额外索引。

### 环境与测量范围

本机 Intel macOS，`darwin/amd64`，Intel Core i7-9750H @ 2.60GHz，Go `1.27.1`。基准名称后缀为 `-12`；每组固定 4 个磁盘图表，另加入 100、1,000 或 10,000 个非磁盘图表，每种场景执行 3 次、每次目标时间 300ms。构造注册表和样本不计入计时，计时包含磁盘筛选、最新值读取、指标计算和结果排序。

这是 **`diskMetricsFor` 局部函数基准**，不包含 HTTP、整份运维快照、真实采集或多节点网络，不能外推成整机 CPU、常驻内存或端到端响应下降。`B/op` 是每次调用的累计分配字节，不是 RSS；少量结果切片动态扩容使分配次数从 25 增至 27，而分配字节明显减少。

### 复现命令

从仓库 `core/` 目录执行。以下为测量时使用的 Go 路径，可替换为 PATH 中相同版本的 `go`；需先按项目流程准备 Go 嵌入的 Web 资源。

```sh
# 优化前：已加入 operations_performance_test.go，diskMetricsFor 仍使用 Charts 后过滤。

  -run '^$' -bench '^BenchmarkOperationsDiskMetrics$' \
```
