# 产品质量提升与验收

本轮以现有代码的用户流程为依据，不以功能数量判断成熟度。目标是让值班人员能发现问题、理解证据、完成处置，并可靠地交接结果。

## 已落地：服务与拓扑工作台

入口：工作区「服务与拓扑」。

- 选择最近 1 小时、24 小时、7 天或 30 天，服务统计与告警统计同时切换；请求取消后不得覆盖新窗口。
- 搜索服务名、关联告警、依赖服务、图表或连接端点。异常筛选显示当前非 CLEAR 服务和窗口内曾触发的告警，拓扑只按搜索词过滤。
- 服务按严重程度优先排序；点击关联告警或依赖名称可继续检索。
- 展示服务数、异常服务数、告警统计数、连接数和上次成功时间。零结果与未配置分别解释。
- 刷新失败保留上次完整快照并标记非实时；已加载窗口和选择窗口分别保留。失败或加载中禁用导出。
- CSV 只包含当前筛选的告警统计，包括图表、未告警占比、告警秒数、窗口秒数与 UTC 时间边界。文本按电子表格公式防护规则转义。
- 窄屏沿用卡片布局，输入和操作区换行，表格转换为标注字段的卡片。

### 数据口径

统计依据服务端保留的告警状态转移历史，不是独立可用性探测。服务百分比取关联项的最小值，不是按多个告警的故障时间并集计算。历史裁剪、采集离线、没有关联告警等场景不具备完整业务 SLA 的证据。因此界面明确标注“未告警占比”，不提供业务 SLA 达标承诺。

## 后续交付队列

| 优先级 | 源码中可确认的差距 | 验收目标 |
| --- | --- | --- |
| P0 | 服务计算缺少无数据状态与观测覆盖信息；告警历史按名称汇总可能混合不同图表 | 无输入不显示健康；不同实例分别计时；覆盖不足明确显示未知，并具有服务端回归测试 |
| P0 | 服务树 API 支持修改，但工作台没有可预览的编辑流程 | 管理员可编辑、校验并预览影响，冲突不覆盖他人配置；只读用户不可写 |
| P1 | 缺少从首次接入到确认采集、通知测试的统一引导 | 新用户能按实际状态完成接入，并明确知道哪些能力尚未验证 |
| P1 | 管理与诊断模块的空状态、加载、重试和错误反馈仍不统一 | 失败可恢复、草稿不丢失、旧数据可辨识；桌面与窄屏验证 |
| P1 | 缺少面向交接的服务级报告 | 导出范围、数据来源、统计口径、缺失区间和处理记录可追溯 |
| P2 | 长时间运行、硬件与多客户端真实环境覆盖尚不完整 | 按发布矩阵积累实际运行证据，不以浏览器模拟替代实机验收 |

## 本轮验证入口

- `make all`：构建 Web 并重新嵌入 Go 服务；使用项目固定的 Node 24.19.0 与 Go 工具链。
- `cd web && npm run test:e2e -- e2e/services.spec.ts e2e/services-workbench.spec.ts`：桌面、手机视口下验证展示、检索、异常筛选、CSV 公式防护、窗口切换、失败旧数据保留及恢复。
- `cd web && npm run test:unit` 与 `npx tsc -p tsconfig.e2e.json`：既有模型回归与浏览器测试类型检查。

浏览器测试使用隔离服务和合成接口夹具，证明交互行为，不代表生产服务的实际 SLA 或手机实机验收。

2026-11-18 验证结果：构建、前端单元测试、架构检查、应用及 E2E TypeScript 检查、文档链接检查通过。浏览器使用已安装的 Chrome（`MONITOR_BROWSER_CHANNEL=chrome`），上述两份用例在 desktop/mobile 项目共 4 项通过；隔离进程正常退出。默认 Playwright 浏览器缓存缺失，未将该环境启动失败计为产品回归通过。
