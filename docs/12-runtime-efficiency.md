# 运维响应与 HTTP 探测优化

进程在打开 TSDB 之前就绑定 `web.listen`。几百兆历史块加载期间，`GET /healthz` 返回 `503` 和正文 `loading`（`Retry-After: 1`），其它路径同样是 `503`。加载结束后 `/healthz` 才返回 `200 ok`。现有等待脚本把非 200 当成还没就绪，会继续轮询，不会把加载中的进程当成可以查询的实例。

2026-09-28，本轮继续降低运维查询的重复工作，并修复 HTTP 探测连接积累和快照导出不一致。默认登录、访问角色及已有持久化格式保持兼容。

## 历史搜索

原实现对每条候选记录拼接全部字段及最多 20 条备注，再统一转小写搜索。现在先匹配操作者条件，再逐字段搜索普通关键词，首次命中即可返回；例如按主机名搜索时，无需再扫描该主机的所有备注。

含换行的关键词仍使用原字段顺序及换行拼接规则，保留跨字段搜索行为。Unicode 仍使用 `strings.ToLower`，没有扩大为其他大小写折叠规则。分页总数、游标、导出和快照失效语义不变。

本机基准使用 Go 1.27.1、Intel Core i7-9750H、darwin/amd64、`GOMAXPROCS=4`。固定 5,000 条记录，每条 20 个 2,048 字节混合大小写 ASCII 备注，分页最多返回 25 条；备注字符串在记录间共享，构造和预热不计时。每组 3 次，目标 200ms，慢用例每次只执行一次。主机其他负载未控制，以下不是生产性能保证。

| 查询 | 优化前耗时 | 优化后耗时 | 单次分配字节前 → 后 |
| --- | --- | --- | --- |
| 主机名命中 | 843–865 ms | 0.564–0.735 ms | 507.9 MB → 73.3 KB |
| 第一条备注命中 | 904–968 ms | 25.3–26.9 ms | 507.9 MB → 10.3 MB |
| 最后一条备注命中 | 1.11–1.36 s | 482–516 ms | 507.9 MB → 204.9 MB |
| 没有匹配 | 1.38–1.47 s | 559–719 ms | 507.8 MB → 204.8 MB |
| 操作者不匹配 | 13.0–16.2 ms | 0.690–1.15 ms | 16.3 MB → 5.44 KB |

分配量使用十进制单位，是每次查询累计分配字节，不是常驻内存。末备注和未命中仍需遍历全部备注，逐字段转小写使分配次数约从 30,000 增至 100,000，但总字节减少约 60%。多行关键词保留原搜索方式，不据其时长波动宣称算法收益。这是内存中历史查询基准，不包含 HTTP、磁盘和采集成本。

在 `core/` 执行以下命令可复测，优化前参考提交为 `3779e13`，需使用相同新增基准文件：

```sh
GOMAXPROCS=4 go test -p 1 ./internal/operations -run '^$' \
  -bench '^BenchmarkHistorySearchLargeNotes$' -benchmem -count=3 -benchtime=200ms
```

## 跨 Hub 告警读取

运维总览此前逐个查询其他 Hub 的节点告警；遇到多个慢节点时，每个节点的超时会累加。现在整个服务共享最多 8 个此类出站请求，每份快照的 peer 请求阶段共用 5 秒预算，包含等待并发槽位的时间。多个浏览器同时刷新也不能各自增加 8 个出站请求。

用户取消读取会中止在途请求并丢弃未启动任务。超时、失败或未读到的节点保留 `unknown` 告警覆盖状态，不当作无告警的健康节点。已有直连和单跳转发认证规则不变。非法列表长度在构建快照前拒绝，避免无效请求触发网络查询。

5 秒是 peer 阶段的预算；本机指标处理、历史读取和 JSON 编码仍另需时间，不表示整个接口严格在 5 秒内完成。

合成基准模拟 16 个节点，每个 HTTP 告警请求固定等待 5ms；不包含目录发现和完整总览处理。3 次、每次 5 个样本：旧串行算法参考耗时 90.1–131.1ms，并发实现 11.9–12.5ms。并发调度与连接增加了单次分配（约 119KB → 218KB），这一项改善的是延迟，不是分配量。

```sh
GOMAXPROCS=4 go test ./internal/api -run '^$' \
  -bench '^BenchmarkOperationsPeerFetch$' -benchmem -benchtime=5x -count=3
```

## HTTP 探测连接与失败判定

`httpcheck` 改为复用连接池。严格 TLS 验证和显式跳过验证的任务使用独立连接池，避免复用未验证的 TLS 连接。每个池最多保留 32 条空闲连接、每个目标最多 2 条，空闲 30 秒后回收；采集器停止时主动关闭空闲连接。

任务自己的请求方法、请求头、接受状态码、超时和禁止自动重定向规则继续生效。响应头是 200，但读取响应体超时或提前截断时，现在记录失败，并保留实际状态码及已读字节数。原有 1 MiB 读取上限保持不变，不检查截断窗口之外的内容。

真实 HTTP 回归验证了 10 次检查只建立 1 条连接，停止后连接关闭；这说明连接复用生效，不代表整机吞吐提升比例。

## 运维页面与导出

- 连续输入搜索文字等待 250ms 再发起请求；输入当刻取消旧请求。枚举筛选和手动刷新立即执行。
- 导出进行时禁止重复提交；文件时间、节点、问题和处理活动均取自本次导出响应。
- 改变筛选、离开运维页或登录失效时取消未完成导出，避免后台突然下载旧文件。
- 读取失败明确显示未生成文件，不再静默使用页面里的旧快照。

## 2026-10-09：告警查询与页面刷新

本轮基于最新主线 `036926f` 优化告警读取和推送，沿用其持续告警、恢复表达式、模板及动作规则。

- 普通 `lookup` 在查询前按维度 ID 或名称筛选，避免读取宽图表中无关的时间序列。`percentage` 仍读取全部维度计算分母。
- `sum` 直接复用本次查询的原始点进行积分，减少一次 TSDB 查询，也避免两次查询跨越新采样时结果不一致。NaN 采样的时间仍用于划分积分区间；空窗口与全 NaN 窗口仍为未知。
- Web 告警快照的在途请求由页面、面板及实时事件共用；告警历史只在面板打开时读取。面板仍每 5 秒刷新阶段，页面隐藏、节点切换和认证状态变化会取消旧读取。
- 无浏览器订阅对应节点时，不再为告警事件分配和编码 JSON；有订阅时只编码一次，图表筛选不影响告警接收，慢客户端仍不会阻塞采集。

下面是本机相同基准前后各 3 次的中位数，Go 1.27.1、darwin/amd64、Intel i7-9750H、`GOMAXPROCS=4`。Lookup 场景为 64 维图表、每维 300 个点、只选 1 维，内存窗口和构造不计入测试，目标每组 300ms。

| 路径 | 耗时前 → 后 | B/op 前 → 后 | allocs/op 前 → 后 |
| --- | --- | --- | --- |
| 单维 average lookup | 1,011,511 → 13,172 ns | 1,130,497 → 18,168 | 641 → 11 |
| 单维 sum lookup | 822,572 → 6,916 ns | 1,417,728 → 12,928 | 321 → 4 |
| 无浏览器的告警推送 | 7,117 → 28 ns | 2,057 → 0 | 14 → 0 |
| 浏览器订阅其他节点的推送 | 7,541 → 76 ns | 2,057 → 0 | 14 → 0 |

`percentage` 的全维度读取开销保留；已有订阅的告警仍需编码。B/op 是单次操作累计分配，不是进程常驻内存。时间受本机并行工作影响，不据此宣称整机 CPU、内存或所有接口同比改善。

## 2026-10-13：合成探测内存与取消处理

HTTP 探测只需记录响应长度，改为有界流式计数，不再为响应内容建立和扩容整个字节切片。继续保留 1 MiB 读取上限、连接复用、独立 TLS 策略，以及响应体超时和截断错误的失败判断。长度仍是最多读取 1 MiB 的字节数，不是无限制下载大小。

HTTP、TCP 端口和 DNS 探测在开始下一目标和发布结果前检查整轮采集上下文。服务停止或整轮采集超时时，停止后续探测并返回取消原因，不将尚未完成的目标写成新的失败/成功样本；已经完成的目标结果保留。单个目标自身超时、而整轮采集仍有效时，仍按原规则记录失败。

DNS 改用支持取消等待的 `LookupIPAddr`，避免 `LookupHost` 在无响应 DNS 服务器上等待套接字截止时间后才结束本轮采集；仍检查 IPv4/IPv6 地址解析结果。

可复测基准（`core` 目录）：

```sh
go test ./internal/collect -run '^$' -bench BenchmarkHTTPCheckResponseCounting -benchmem -benchtime=100x -count=3
go test -race ./internal/collect -run 'TestHTTPCheck|TestCancelledSyntheticChecks|TestDNSCheck|TestPortCheck'
```

2026-10-13，macOS amd64、Intel i7-9750H、Go 1.27.1，同一进程内模拟 HTTP transport，预建响应内容，三次各 100 次调用：

| 响应大小 | 优化前分配/次 | 优化后分配/次 | 分配次数变化 |
| --- | --- | --- | --- |

这是 `httpcheck.do` 路径的微基准，包含请求、上下文和模拟响应对象，不包含真实网络、TLS、图表存储或整机采集开销；不据此外推整机 CPU/RSS 降幅。回归包含取消前/取消中的探测、真实本地 UDP DNS 取消、部分完成后取消、空响应及响应上限，并复用既有连接复用、TLS、响应体截断和目标超时测试。

## 2026-10-13：历史中位数聚合内存

中位数聚合只保留每个汇总桶的均值，不再保留整份包含时间、最小值、最大值、总和、末值和计数的记录；原始数据与汇总数据都直接排序查询独占的临时数值，省去排序前复制。调用方传入的历史数据不会被修改。汇总层仍采用“各桶均值的中位数”，没有改成加权中位数；空槽、NaN、正负无穷的处理与之前一致。

排序只在全部数据块处理完成后进行，保留解码失败时按长度回退的能力。回归覆盖奇偶样本、重复值、不同计数的汇总、多序列独立性、输入不可变性、原始/汇总损坏块和重启后的查询。

macOS amd64、Intel i7-9750H、Go 1.27.1，同一组预建输入、600 个显示点，前后各三轮、每轮 100 次：

| 查询场景 | 优化前分配/次 | 优化后分配/次 | 分配次数变化 |
| --- | --- | --- | --- |
| 一天原始数据（86,400 个样本） | 约 3,170,500 B | 约 2,479,300 B | 6005 → 5405 |
| 一周分钟汇总（10,080 个桶） | 约 1,825,500 B | 约 298,150 B | 4685 → 3485 |

上述分别减少约 22% 和 84% 的分配字节，是聚合函数微基准，不包含磁盘读取、HTTP 序列化或浏览器渲染，不代表整机 RSS 或响应时间降幅。复测：

```sh
cd core
go test ./internal/tsdb -run '^$' -bench '^BenchmarkMedianAggregation$' -benchmem -benchtime=100x -count=3
go test -race ./internal/tsdb
cd ..
make all
python3 scripts/verify-durability.py --group median --points 2
```

持久化脚本支持指定聚合函数与显示点数，默认行为保留为平均值、100 点；使用两点中位数查询检查真实服务在崩溃恢复、备份还原后的历史值一致性，避免只检查单样本桶。

本轮隔离服务验证通过：中位数两点查询与默认平均值查询均通过崩溃恢复、运行中备份拒绝、备份还原检查；测试服务及数据均由脚本清理。
