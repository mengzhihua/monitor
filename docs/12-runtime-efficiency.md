# 运维响应与 HTTP 探测优化

进程在打开 TSDB 之前就绑定 `web.listen`。几百兆历史块加载期间，`GET /healthz` 返回 `503` 和正文 `loading`（`Retry-After: 1`）。其它连接在加载完成前直接断开，验收脚本会像端口还没打开时一样重试。加载结束后 `/healthz` 才返回 `200 ok`。

2026-09-28，本轮继续降低运维查询的重复工作，并修复 HTTP 探测连接积累和快照导出不一致。默认登录、访问角色及已有持久化格式保持兼容。

## 历史搜索

原实现对每条候选记录拼接全部字段及最多 20 条备注，再统一转小写搜索。现在先匹配操作者条件，再逐字段搜索普通关键词，首次命中即可返回；例如按主机名搜索时，无需再扫描该主机的所有备注。

含换行的关键词仍使用原字段顺序及换行拼接规则，保留跨字段搜索行为。Unicode 仍使用 `strings.ToLower`，没有扩大为其他大小写折叠规则。分页总数、游标、导出和快照失效语义不变。

本机基准使用 Go 1.27.1、Intel Core i7-9750H、darwin/amd64、`GOMAXPROCS=4`。固定 5,000 条记录，每条 20 个 2,048 字节混合大小写 ASCII 备注，分页最多返回 25 条；备注字符串在记录间共享，构造和预热不计时。每组 3 次，目标 200ms，慢用例每次只执行一次。主机其他负载未控制，以下不是生产性能保证。

| 查询 | 优化前耗时 | 优化后耗时 | 单次分配字节前 → 后 |
| --- | --- | --- | --- |
| 主机名命中 | 843–865 ms | 0.564–0.735 ms | 507.9 MB → 73.3 KB |
| 第一条备注命中 | 904–968 ms | 25.3–26.9 ms | 507.9 MB → 10.3 MB |
| 最后一条备注命中 | 1.11–1.36 s | 482–516 ms | 507.9 MB → 204.9 MB |
| 没有匹配 | 1.38–1.47 s | 559–719 ms | 507.8 MB → 204.8 MB |
| 操作者不匹配 | 13.0–16.2 ms | 0.690–1.15 ms | 16.3 MB → 5.44 KB |

分配量使用十进制单位，是每次查询累计分配字节，不是常驻内存。末备注和未命中仍需遍历全部备注，逐字段转小写使分配次数约从 30,000 增至 100,000，但总字节减少约 60%。多行关键词保留原搜索方式，不据其时长波动宣称算法收益。这是内存中历史查询基准，不包含 HTTP、磁盘和采集成本。

```sh

```

## 跨 Hub 告警读取

运维总览此前逐个查询其他 Hub 的节点告警；遇到多个慢节点时，每个节点的超时会累加。现在整个服务共享最多 8 个此类出站请求，每份快照的 peer 请求阶段共用 5 秒预算，包含等待并发槽位的时间。多个浏览器同时刷新也不能各自增加 8 个出站请求。

用户取消读取会中止在途请求并丢弃未启动任务。超时、失败或未读到的节点保留 `unknown` 告警覆盖状态，不当作无告警的健康节点。已有直连和单跳转发认证规则不变。非法列表长度在构建快照前拒绝，避免无效请求触发网络查询。

5 秒是 peer 阶段的预算；本机指标处理、历史读取和 JSON 编码仍另需时间，不表示整个接口严格在 5 秒内完成。

合成基准模拟 16 个节点，每个 HTTP 告警请求固定等待 5ms；不包含目录发现和完整总览处理。3 次、每次 5 个样本：旧串行算法参考耗时 90.1–131.1ms，并发实现 11.9–12.5ms。并发调度与连接增加了单次分配（约 119KB → 218KB），这一项改善的是延迟，不是分配量。

```sh
GOMAXPROCS=4 go test ./internal/api -run '^$' \
  -bench '^BenchmarkOperationsPeerFetch$' -benchmem -benchtime=5x -count=3
```

## HTTP 探测连接与失败判定

`httpcheck` 改为复用连接池。严格 TLS 验证和显式跳过验证的任务使用独立连接池，避免复用未验证的 TLS 连接。每个池最多保留 32 条空闲连接、每个目标最多 2 条，空闲 30 秒后回收；采集器停止时主动关闭空闲连接。

任务自己的请求方法、请求头、接受状态码、超时和禁止自动重定向规则继续生效。响应头是 200，但读取响应体超时或提前截断时，现在记录失败，并保留实际状态码及已读字节数。原有 1 MiB 读取上限保持不变，不检查截断窗口之外的内容。

真实 HTTP 回归验证了 10 次检查只建立 1 条连接，停止后连接关闭；这说明连接复用生效，不代表整机吞吐提升比例。

## 运维页面与导出

- 连续输入搜索文字等待 250ms 再发起请求；输入当刻取消旧请求。枚举筛选和手动刷新立即执行。
- 导出进行时禁止重复提交；文件时间、节点、问题和处理活动均取自本次导出响应。
- 改变筛选、离开运维页或登录失效时取消未完成导出，避免后台突然下载旧文件。
- 读取失败明确显示未生成文件，不再静默使用页面里的旧快照。

## 2026-10-25：TSDB 汇总缓冲的存活堆

此前的原始层缓冲回收没有覆盖汇总层。`tier.flush` 归档完成后执行 `done[i:]`，即使结果 `len=0, cap=0`，切片仍可能引用原来的底层数组；保留期裁剪也有同样问题。原始层的 `compactTail` 仅观察裁剪后的容量，因此 `3600` 个样本只剩末尾一个时，看到的是 `len=1, cap=1`，却仍保留整块分配。

现在从裁剪前的容量决定是否复制存活尾部，空尾部设为 `nil`；较小裁剪将尾部移回数组起点，让后续保留期裁剪仍能看到实际容量。原始层和汇总层的归档、保留期裁剪共用这条规则。归档失败仍保留内存数据；并发写入期间到达的新样本按时间戳保留。

`Store.Flush` 是 checkpoint，负责将未满的活动块写入可恢复快照，**不驱逐活动数据**。`tier.flush` 才把已完成的汇总桶归档成独立块并释放相应缓冲。二者不能混称，也不能用 checkpoint 的压缩文件大小代替进程存活堆。每个 `Bucket` 在此平台占 48 字节；旧默认每序列的归档触发阈值是 1440 个分钟桶和 720 个小时桶，切片扩容还会增加容量，写盘失败或并发追加也可能暂时超过阈值。

下表来自 Go 1.27.1、darwin/amd64、Intel i7-9750H、`GOMAXPROCS=2`。探针为两层各 2,000 条序列，将每条序列填到各自块上限之前；每阶段执行 GC，用 `runtime.MemStats.HeapAlloc` 减去空探针基线，且测量时 Store 仍然可达。归档阶段实际写入 4,000 个块。数值是 **存活堆增量，单位 MiB**，不是 `alloc_space`、总分配量、RSS 或生产服务的长期实测。

| 实现 / 分钟、小时块大小 | 接近块满 | checkpoint 后 | 汇总归档后 |
| --- | ---: | ---: | ---: |
| 修复前，1440 / 720 | 266.51 | 266.59 | 266.64 |
| 仅回收修复，显式保持 1440 / 720 | 266.51 | 266.59 | 1.70 |
| 候选 120 / 48 | 18.46 | 18.48 | 1.03 |
| 候选 360 / 168 | 71.20 | 71.22 | 0.99 |

修复前归档后的 `inuse_space` profile 中，`tier.append` 占 272.19 MiB / 99.63%；它是采样估计，与 `MemStats` 精确计数不完全一致。保留旧块大小应用回收修复后，该 profile 中 `tier.append` 只剩约 0.5 MiB 的采样估计，主要对象已变成系列与磁盘索引。未取得用户原机器的序列数、完整 profile、运行时长及 RSS 构成，不能据本机复现声称已解释或消除原机器全部 280–340 MB RSS。

### 块大小的磁盘和索引代价

缩小块会减少活动桶内存，也会增加块文件、fsync 和查询所需的文件读取。固定逻辑历史探针使用 16 条序列，每条输入 1440 个分钟桶和 720 个小时桶，最后归档尾块；各候选输入完全相同。下面为单次本机测量，耗时受磁盘及并发负载影响，不是生产吞吐保证。

| 分钟 / 小时块大小 | 文件数 | 有效文件字节 | 落盘耗时 |
| --- | ---: | ---: | ---: |
| 1440 / 720 | 32 | 343,504 | 1.35 s |
| 120 / 48 | 432 | 321,984 | 19.21 s |
| 360 / 168 | 144 | 332,448 | 6.16 s |
| 720 / 360 | 64 | 338,800 | 2.68 s |

另一个合成探针只构造完整保留期的内存块索引：2,000 条序列、分钟层 90 天、小时层 730 天，包含指向临时目录的完整路径字符串，不创建数据文件。旧大小为 230,000 个块、54.78 MiB 索引存活堆；120/48 为 2,890,000 块、613.49 MiB；360/168 为 930,000 块、220.67 MiB；720/360 为 458,000 块、116.51 MiB。路径长度、活跃序列和实际保留量会改变结果；该模型说明不能仅按短期活动桶堆大小选择默认值。

最终默认选择 **720 个分钟桶 / 360 个小时桶**，连续有数据时分别覆盖 12 小时 / 15 天；采样分辨率与保留时长保持不变。在上述接近块满探针中，存活堆从 266.51 MiB 降至 125.89 MiB，减少约 52.8%。这个折中约将长期文件数翻倍，而非选用 120/48 或 360/168 的四倍至十余倍文件数。它会增加归档和历史查询 IO，不能称为所有性能维度同时改善；已有大块文件继续直接读取，不强制重写整个历史。

已有块与 checkpoint 格式没有改变。加载使用较大块设置写入的 checkpoint 时，达到或超过当前块大小的完成桶会先归档，避免不再采样的旧序列永久保留大缓冲。显式 `tsdb.Options.Tiers[].BlockSize` 继续生效；daemon YAML 当前没有该块大小字段，不能把 Go API 选项当作已有用户配置项。

首次加载这类旧 checkpoint 可能因同步归档而变慢；归档失败会使 `Open` 返回错误，旧 checkpoint/WAL 不会因此被移除，需要恢复目录写入能力后重试。已经存在的历史块不参与这次重写。

### 复测

在 `core/` 执行，profile 输出到自行选择的临时目录：

```sh
GOMAXPROCS=2 GOFLAGS=-p=2 MONITOR_TSDB_HEAP_PROFILE_DIR=/tmp/monitor-tsdb-heap \
  go test ./internal/tsdb -run '^$' -bench '^BenchmarkRollupResidentHeap$' -benchtime=1x
go tool pprof -top -sample_index=inuse_space /tmp/monitor-tsdb-heap/flushed.pprof
# 隔离回收修复效果，显式保持旧块大小：
GOMAXPROCS=2 GOFLAGS=-p=2 MONITOR_TSDB_HEAP_LEGACY_BLOCKS=1 \
  go test ./internal/tsdb -run '^$' -bench '^BenchmarkRollupResidentHeap$' -benchtime=1x
GOMAXPROCS=2 GOFLAGS=-p=2 go test ./internal/tsdb -run '^$' \
  -bench '^BenchmarkRollup(HistoryIO|RetainedIndex)$' -benchtime=1x
GOMAXPROCS=2 GOFLAGS=-p=2 go test -race ./internal/tsdb
```

回归覆盖空缓冲释放、仅剩一个值时的大数组引用、连续保留期裁剪、归档期间并发写入，以及旧大块 checkpoint 加载、归档后再次重启的去重、原始/汇总查询一致和后续追加。以上探针不代替真实部署的长时间 RSS、查询延迟及 inode 使用观测。
